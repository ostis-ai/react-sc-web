# **Стандарт Технологии OSTIS**

Репозиторий содержит исходные файлы документации Технологии OSTIS, оформленной в виде исходного текста Базы знаний Метасистемы OSTIS. База знаний представляет собой иерархическую систему связанных между собой формальных моделей предметных областей и соответствующих
им онтологий. Также данную работу можно рассматривать как проект стандарта семантических моделей
интеллектуальных компьютерных систем.

Исходный текст стандарта разрабатывается при помощи набора [команд](https://github.com/ostis-ai/scn-latex-plugin) языка LaTeX, специально разработанных для оформления научных результатов в виде формальных текстов баз знаний, как это предлагается в рамках Технологии OSTIS.

## **Установка**

Скачать локальную копию репозитория и его подмодулей можно выполнив следующие команды:
```
git clone https://github.com/ostis-ai/ostis-standard.git
cd ostis-standard
git submodule update --init --recursive
``` 

> Инструкции ниже рассчитаны на работу в **основанных на Debian дистрибутивах Linux**.

### Установка зависимостей

Для работы необходимо установить [TexLive](https://tug.org/texlive/)-пакеты и редактор LaTeX:

```
sudo apt-get update
sudo apt install texlive-full
```

### Сборка

Собрать стандарт с получением `.pdf` файла можно следующей командой:

```
latexmk -pdf -silent -synctex=1 "book"
```

Результатом сборки будет файл `book.pdf`.

## **Как внести свой вклад**

Данный раздел описывает то как вы можете внести свой вклад в развитие Стандарта Технологии OSTIS.

Работа ведется через предложения изменения кода (Pull Request, дале скоращенно PR). Далее будут рассмотрены шаги, для создания своего PR и работе с ним.

### Инициализация

Для инициализации вашего репозитория:

* Создайте копию репозитория проекта своем пространстве имён (fork) `https://github.com/ostis-ai/stis-standard`.
* Склонируйте созданную копию себе на машину.

Для клоинрования и добваления исходного репозитория Стандарта в качестве иточника (upstream, который в дальнейшем можно будет использовать для получения обновлений) можно использовать команды:
```sh
git clone git@github.com:yourlogin/ostis-standard.git
cd ostis-standard
git remote add upstream git@github.com:ostis-ai/ostis-standard.git
```

В случае если на вашем устройстве не настроен ssh, можно использовать https:
```sh
git clone https://github.com/yourlogin/ostis-standard.git
cd ostis-standard
git remote add upstream https://github.com/ostis-ai/ostis-standard.git
```

* При необходимости обновления вашей ветки `main` из `upstream` используйте:

```sh
git fetch upstream
git checkout upstream/main
```

* Используйте `git rebase` вместо `merge`. Документацию к `git rebase` можно увидеть [по ссылке](https://git-scm.com/docs/git-rebase). Для того чтобы выполнить `rebase` вашей ветки на main из `upstream`:

```sh
git checkout <yourbranch>
git rebase upstream/main
```

* В случае возникновения проблем (например, при разрешении конфликтов) `rebase` можно отменить:

```sh
git rebase --abort
```

* Задать вопрос при возникновении пробелм можно в [Element](https://app.element.io/index.html#/room/#ostis_tech_support:matrix.org).

## Формат коммитов

Название коммитов должны формироваться по следующей схеме: `[tag1]...[tagN] Текст названия (#issue)`.

Текст названия коммита должен начинаться с большой буквы. Если коммит исправляет или реализует какое-то из #issue, то оно должно быть указано в названии.

Каждый коммит в PR должен быть атомарным. Другими словами, он должен реализовывать или исправлять один аспект. Например:

```
[content] Update key elements in subject domain of agents
[content] Update key elements in subject domain of problem solvers
[content] Add additional examples in subject domain of problem solvers
[translated] Update files with recent changes
```

В данном примере мы обновили перечень ключевых элементов, рассматриваемых в пр. о. агентов и решателей задач, а также добавили несколько примеров в пр. о. решателей задач. Также были обновлен результат трансляции стандарта в `.scs` c учетом данных изменений.

Допустимые теги:
* `[content]` - измененеие в находящимся в `Contents` содержимом .tex версии стандарта;
* `[translated]` - изменение `.scs` фалов в `translated_scs`, являющихся результатом трансляции стандарта;
* `[refactor]` - рефактор кода;
* `[review]` - коммиты с исправлниями полученных в ходе рецензирования замечаний;
* `[bulid]` - изменения в корневых файлах, задающих конфигурацию для сборки;
* `[specification]` - изменения в спецификации стандарта как многократно используемого коспонента;
* `[docs]` или `[doc]` - изменения в докумнетации, включая README файл;
* `[ci]` - изменения в конфигурации или скриптах, связанных с `ci`;
* `[git]` - изменения в конфигурации `git`.

Каждый отдельный коммит не должен содержать большого объема изменений, за исключением:
* Изменение стиля оформление и форматирование кода;
* Переименования.

**При этом даже в случае указанных выше исключений, каждый коммит все еще должен быть атомарным.** Например если хотите изменить основной идентификатор (и все его использования) `сущности А` и `сущности Б`, то используйте для этого два отдельных коммита:
```
[content] Change main identifier of entity A
[content] Change main identifier of entity B
```

**НЕ смешивайте стилистические и смысловые изменния в одном коммите.**

Все коммиты которые не следуют данным правилам должны быть работы для соответствия им. В ином случае PR с ними будет отклонен.

## Процесс работы с PR

Работа с PR выполняется следующим образом:
- Создайте PR;
- Рецензенты проверяют корректную сборку кода из PR;
- Рецензенты оставляют свои отзыв в виде набора комментариев;
- Автор вносит исправления в виде коммитов с тегом `[review]`;
- Автор запрашивает повторный отзыв;
- Рецензенты отмечают комментарии которые были исправлены как разрешенные и одобряют PR если все проблемы устранены.
